The problem

Every 0.3 s a shopper arrives.
We have 3 seconds to choose the 10 products they see.

Today: everyone sees the same best sellers

  • A first-time visitor looking at running shoes gets the same carousel as a returning customer browsing garden tools.
  • The list never reacts: not to a product that is suddenly trending, a price drop, or a product launched an hour ago.
  • And if one listed product is out of stock, the whole answer is thrown away.

What success means

More purchases per 100 shoppers than the best-seller list, measured against the best list a perfect system could pick for each shopper: 0 = best sellers, 100 = perfect. Answers must be valid and on time; a late answer is replaced by the best sellers.

HOW THE 100 POINTS ARE SPLIT

Scored only in the 2-hour final, on new shoppers, new products and new trends.

What we built

A recommender that reads the session, ranks by purchase probability, and never misses a deadline

Generalises

The model never memorises product or shopper IDs. It learns relationships (same category as what you viewed, price you usually pay, trending now), so it works for shoppers and products it has never seen, which is what the final is.

Fast by design

No database query on the critical path: everything a request needs is already in memory. The database is read in the background.

Cannot fail silently

Three safety nets: full model → simple session rules → safe best-seller list. A standby machine takes over if the main one stops sending heartbeats.

Method · how we knew before going live

Nothing reached shoppers without first winning offline, then winning live

1 · Learn from the old system's log

60 days, 2 M carousel impressions with clicks and purchases. The old system showed mostly popular items, so the log is biased. We correct for that with the recorded propensities (how likely each item was to be shown), so we can estimate how a new list would have done.

2 · Check the checker

We built a simulated shop where the true purchase probability is known, and verified that our offline estimate recovers it before trusting it on real data.

3 · One promotion rule

A version goes live only if it beats the current one on the same replay, without hurting new shoppers, with zero errors and p99 latency under 1.8 s. Live, it must win an A/B test with 95 % confidence.

Learning from the stream · using RawTree

The shop changes every minute, and so does what we show

  • Trends: every view, cart and purchase updates a "popular right now" score that forgets in minutes (8-minute half-life), so a product taking off moves up quickly.
  • Prices and stock: applied within half a second. A sold-out product disappears from every list, and a price drop is a signal.
  • New shoppers: what they view in this session is their whole history, used from the first click.
  • New products: no sales yet, so they borrow the record of similar products (same subcategory, brand, price) until their own data arrives.
  • Our own results: per-product calibration (did it sell as often as we predicted?), cheap exploration on slots 9–10 only, A/B tests with a promotion rule.

RawTree is the system's memory and its monitor

  • Features in SQL: co-views, popularity by context, position bias and propensity-corrected conversion are computed inside RawTree over 12 M events (rtrec/sql).
  • Reads: incremental cursors on requests, events, catalogue updates and feedback, with one persistent connection.
  • Writes: batched answers every ~0.2 s, retried without ever duplicating. Heartbeats go to scratch, so the standby knows when to take over.
  • Monitoring: every dashboard number also has a SQL version that runs in RawTree, and the two are checked against each other.
